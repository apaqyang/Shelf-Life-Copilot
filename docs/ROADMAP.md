# Project Roadmap and Target Architecture

> 文档性质：公开工程规划
> 当前基线：v0.1
> 更新日期：2026-09-23
> 配套文档：[ARCHITECTURE.md](ARCHITECTURE.md) · [TECH_SPEC.md](TECH_SPEC.md) · [DEVELOPMENT_TASKS.md](DEVELOPMENT_TASKS.md)

本文档回答两个问题：项目下一步向哪里演进，以及演进后的系统边界应该是什么。当前代码结构与依赖方向以 `ARCHITECTURE.md` 为准，可执行任务以 `DEVELOPMENT_TASKS.md` 为准。

---

## 1. 当前基线

已实现的核心链路：

- JSON 批次与客户配置加载，并提供 `BatchRepository` 插件边界。
- 临期阈值分级、LLM 建议生成、越界动作标记和卡片渲染。
- Anthropic、Moonshot 和零配置 offline provider。
- 每日扫描、每月报告调度，统一使用 `Asia/Shanghai` 业务时区。
- SQLite 决策与建议日志、PDF 月报、企微群机器人推送。
- FastAPI 生命周期管理、企微点击回调骨架、企业插件加载机制。
- Python 3.11/3.12 CI，核心测试保持 100% 语句和分支覆盖。

当前定位是“可离线演示、可审计、可通过插件扩展”的开源核心，还不是默认可暴露到公网的多租户服务。

---

## 2. 演进原则

1. **建议与执行分离**：LLM 只生成建议，真实处置始终需要显式决策和可追溯工单。
2. **业务层不感知供应商**：ERP、LLM、企微和存储通过 protocol/port 接入。
3. **多租户数据显式带 `customer_id`**：不依赖请求上下文或隐式全局状态推断租户。
4. **时间值全部可追溯**：持久化统一 UTC，报表和调度使用明确的业务时区。
5. **失败可见且局部隔离**：单批次、单客户或单次推送失败不应阻断其他任务。
6. **默认安全**：生产回调必须验签、鉴权、限流并具备幂等性；明文模式只用于本地自测。
7. **保持小步迁移**：新基础设施先实现现有 protocol，再切换生产组装，不重写领域规则。

## 3. 目标架构

```text
┌────────────────────────────────────────────────┐
│ Entry adapters                                 │
│ CLI · FastAPI · APScheduler · WeCom callbacks   │
└───────────────────────┬────────────────────────┘
                       │
                       ▼
┌────────────────────────────────────────────────┐
│ Application services                            │
│ Scan · Revise · Decide · Work order · Report │
└───────────────────────┬────────────────────────┘
                       │
          ┌─────────────────────┼─────────────────────┐
          ▼                     ▼                     ▼
┌───────────────┐ ┌───────────────┐ ┌───────────────┐
│ Domain        │ │ Ports         │ │ Observability │
│ models/rules  │ │ repository    │ │ logs/metrics  │
│ invariants    │ │ LLM/WeCom     │ │ audit/events  │
└───────────────┘ │ persistence   │ └───────────────┘
                  └───────────────┘
                         │
                         ▼
┌────────────────────────────────────────────────┐
│ Infrastructure adapters                         │
│ JSON/ERP · Anthropic/Moonshot/local LLM       │
│ SQLite/PostgreSQL · WeCom bot/app             │
└────────────────────────────────────────────────┘
```

### 3.1 目标边界

| 边界 | 责任 | 不应承担 |
|---|---|---|
| Entry adapters | 协议解析、认证、参数校验、响应转换 | 预警或 ROI 规则 |
| Application services | 组织用例、事务边界、幂等性、失败隔离 | 供应商 SDK 细节 |
| Domain | 数据契约、阈值分类、状态转移和业务不变量 | 文件、网络或数据库 I/O |
| Ports | 定义外部能力的最小接口 | 具体部署选型 |
| Infrastructure adapters | 连接 ERP、LLM、企微、数据库和文件系统 | 重复领域规则 |
| Observability | 结构化日志、指标、追踪和审计事件 | 改变业务结果 |

### 3.2 核心数据流

```text
Batch source -> scan -> alert -> suggestion -> card -> decision
                                                   |
                                                   v
actual result <- work-order receipt <- work order <-+
       |
       v
monthly aggregation -> PDF/summary -> delivery
```

每个状态变化都应有稳定标识、租户标识、UTC 时间戳和来源信息，以支持幂等处理与审计。

## 4. 阶段规划

### M0 · 可重现开源基线（已完成）

目标：无外部账号即可运行完整演示链路。

验收门槛：

- offline provider 可扫描示例批次并渲染卡片。
- 决策和建议可持久化，月报可由 SQLite 数据生成。
- 定时任务、推送、回调和插件加载有自动测试。
- 核心模块语句和分支覆盖率为 100%。

### M1 · 单租户生产加固

目标：让单个客户的私有化部署具备可恢复、可观测和可升级能力。

验收门槛：

- SQLite schema 有显式版本和可重复执行的迁移。
- 企微回调具备验签、幂等键、重放保护和可配置限流。
- 扫描、推送和报告有结构化日志、correlation ID 和最小运行指标。
- 备份恢复、密钥轮换和版本回滚有可验证的运维步骤。

### M2 · 决策闭环

目标：从“提醒 + 建议”演进到“决策 + 工单 + 回执 + 复盘”。

验收门槛：

- 改方案文本可关联到原建议，且仅触发一轮受控重生成。
- 同意决策会产生工单，工单状态转移有明确规则和审计记录。
- 完成回执可记录实际数量和实际节省，不覆盖原始估算。
- 月报可区分估算、已执行与已核实数据。

### M3 · 集成与多租户

目标：在不改变领域层的前提下接入真实 ERP，并支持多客户管理。

验收门槛：

- ERP 适配器通过统一契约测试，包含分页、重试、超时和错误映射。
- API 认证后的租户身份与路径、请求体中的 `customer_id` 一致。
- PostgreSQL 适配器通过与 SQLite 相同的持久化契约测试。
- 任务调度、日志、指标和数据查询均可按租户隔离。

### M4 · 规模化与优化

目标：在有足够真实决策数据后，提升吞吐、成本与建议质量。

验收门槛：

- 批次并发有明确上限、退避和 provider 限流保护。
- 本地 LLM 与云端 provider 使用同一契约与质量评估集。
- 跨批次联合建议使用独立用例和数据模型，不破坏单批次流程。
- 在加载测试下达到事先定义的延迟、失败率与成本预算。

## 5. 关键迁移路径

### 5.1 SQLite 到 PostgreSQL

1. 先为 Decision/Suggestion 存储定义 protocol 和共享契约测试。
2. 引入 SQLite schema version，保持现有用法不变。
3. 实现 PostgreSQL adapter，运行同一套契约测试。
4. 在组装层通过配置选择 adapter，最后再做数据迁移。

### 5.2 明文回调到生产回调

1. 保留 `PlaintextCrypto` 作为本地测试适配器。
2. 生产环境在启动时强制检查 AES 回调插件。
3. 把回调解密、去重和业务处理拆成独立边界。
4. 对重放、乱序、重复和部分失败建立端到端测试。

### 5.3 单步决策到工单闭环

1. 先定义 `WorkOrder` 模型和状态机。
2. 使“同意”事件以幂等方式创建工单。
3. 接入完成回执和实际节省数据。
4. 最后调整月报聚合口径，保留历史数据可解释性。

---

## 6. 非目标

在 M1-M3 完成前，不将以下事项作为核心优先级：

- 通用 BI 仪表盘或复杂前端管理后台。
- 自动执行库存处置，绕过人工决策。
- 未有评估数据支撑的大规模 prompt 重写。
- 为单一 ERP 实现侵入核心领域层的特例。
